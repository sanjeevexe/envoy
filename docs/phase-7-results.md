# Phase 7 results: the final evaluation

**Status (Oct 27, night): measurement pass under way; not the final numbers.** The final numbers come from one run of every suite on the frozen commit, tagged `eval-final` on Nov 2. Until then this file records what the measurement passes found and what changed because of it. Plan: `prompts/phase-7-plan.md`. Report: `eval/results/final/report.md`.

## What was built

All of it is Envoy's own code (about 2,300 lines of Python in `eval/` and `backend/`, plus a small SkyLark change); matplotlib draws the charts.

| Part | Where | What it does |
| --- | --- | --- |
| One command per suite | `eval/run_final.py`, `eval/run_final.sh` | compile, systems, repeats, change, sizes, real, memory, safety, injection, interfaces, report; the script runs them in order with one emulator of ours at a time |
| Suite records | `eval/final_common.py` | Each suite's JSON says the commit (and whether it is the `eval-final` tag), the tier, the devices, and the model calls, tokens and dollars it caused, summed from the cost log by the suite's task-ID prefix so nothing else on the Mac is counted |
| The core set over seeded worlds | `eval/final_core.py` | Phase 1's 10 tasks, each asked about a booking, past trip or balance the routine has never seen; a world is one seed's SkyLark state (4 new bookings below the next trip, 3 new past trips spread through the list, a new balance). Every run fails on any side effect in the app the request didn't ask for |
| The three systems | `eval/final_core.py` | Full agent; fixed replay (recorded taps, a similarity check, the agent on a mismatch); Envoy routines through the product's own path (the matcher, then the routine with repair and the agent behind it, patches on trial) |
| Safety suite | `eval/final_safety.py`, `eval/capture_safety.py` | 20 irreversible and ~20 reversible controls on captured SkyLark and real-app screens, classified by the code signals, the model's label and the gate; live declines; planted instructions on SkyLark's screens (a fixture-driven notice card) and in the test inbox |
| Memory suite | `eval/final_memory.py` | Extraction on labeled emails, screens and screenshots; entity matching; stale facts served at four ages |
| Report | `eval/final_report.py` | `report.md`, the design's success targets measured, and the charts |

## What the evaluation found, and what changed (so far)

1. **The compiler dropped the answer of a routine with no steps.** "How many SkyLark miles do I have?" is answered on the screen the app opens to, so the agent's run had no actions. Outputs are read by steps, so the routine promised `miles` and could never read it: verification rejected it three times. A routine whose answer is on the first screen now gets one read-only step that carries its outputs. Test: `test_an_answer_on_the_start_screen_still_compiles_to_a_step_that_reads_it`.
2. **The product never patched its routines.** Local repairs became versions on trial only in the evaluation harness; the API's runner ran routines and discarded their patches. `routines/lifecycle.py` is now shared: a repaired run puts its patches on trial, the next run decides it (active if it runs with no model call, rolled back otherwise).
3. **Memory said "yesterday" for a fact seen 10 days ago.** The notes gave old facts a bare date ("Oct 27"), and the model turned it into a relative age against its own idea of today. Notes now give the age ("10 days ago (Oct 27)") and the answer step gets the current time.
4. **One-time screens stay optional.** Play Store's interests onboarding and Calendar's welcome pages were compiled as required steps, so the routine waited for screens that never return. Steps that only get past a one-time screen (Skip, Not now, Got it, or Wonder's own words for an onboarding or welcome step) compile as optional, and a run of optional steps is skipped when the first required step after them is ready.
5. **List rows use the app's own separators.** "Queen • 5:55 • 2.7B plays" was read whole because only Envoy's " · " split a row into parts; " • " and " | " split it too.
6. **The Contributor tier's model behaved differently.** On SkyLark's check-in the Contributor model backed out of an enabled Continue button again and again ("Wrong action placeholder - need correct JSON") and hit the step limit; the standard model did the same task in 10 actions. Measurement passes therefore run on the standard tier (the side-by-side is in the report, section 1c).
7. **Fixed replay takes irreversible actions without approval.** Replaying recorded taps bypasses the policy gate: on the original layout it checked in and changed the seat on the recorded booking (Denver) instead of the requested one, with no approval asked. That is the baseline's nature (Mobilerun-style macros), and part of why routines carry their own risk labels and gate.
8. **A tap at a point skipped the code half of the policy gate.** On SkyLark's captured screens the rules caught all 6 irreversible buttons when tapped by element number, and none when the same tap came as a point (`tap_point`), where only the model's own label stood guard. A point is now judged as a tap on the element under it. The same suite found rule gaps on real-app screens (uninstall, erase, reset, a buy button that is only a price, the dialer's call button, a bare "OK" confirming an uninstall): rules and a "destructive confirmation" screen signal now cover them. The suite reports the classifier as Phase 6 left it beside the new one, on the same screens.
9. **Placeholder taps can't be produced any more.** On 18 real-app runs the step model sent 55 `tap_point`s, 51 on screens that listed their elements with no screenshot (rejected by the runtime, each a wasted call: "tap_point 500,500 · Advance past welcome screens" eight times beside a listed "Got it"). Where the runtime would reject one, the step call now uses a schema without `tap_point`, so structured output can't emit it.
10. **The first search result is chosen by its place.** Gmail's search routine opened the first row *containing* the search term (another email), because the row showed the term the agent had typed. The top row of results for a value typed in the run now compiles to its place in the list; a row that is the value itself ("Caffè Latte") stays chosen by the input.
11. **An inferred answer is reported as the words it came from.** Contacts answered "0" from "No contacts yet", which never appears as a value, so the routine learned no output. It now reports the screen text.
12. **A patch copied one booking into a check.** The repeats suite (10 requests per task) found find_trip failing on requests 4 and 5: on request 2 a relaxed match rewrote a check from that run's row ("Savannah", `trip_row_6PBKDJ`); the trial passed on request 3 and the patch went live. A check bound to an input is no longer rewritten from a run's screen. The fallback agent also gets the user's own request now, not the routine's intent (it had backed out of the app and got stuck on the home screen).

13. **Checks past the edge of the screen.** With a notice card on the trip page, "Known traveler number saved" appeared below the screen's edge: the number was saved, but the Save step's checks failed and the fallback agent took over. After-checks about what is shown, and the routine's final check, now scroll to look before the ladder goes on (no model call). On the same run, pressing Back to close the keyboard (an earlier attempt at this fix) also left the trip page in Compose, so a target under the keyboard is now scrolled out from under it instead.
14. **Long rows were read from the model's 120-character view.** A status line padded with planted text pushed the gate and departure time past the clip, and the routine lost them. Elements keep their whole text beside the clipped label, and outputs are read from it.
15. **Amazon labels Add to Cart and Buy Now both "Submit".** Told apart only by their IDs (`add-to-cart-button`, `buy-now-button`), so the rules flagged both (over-asking on Add to Cart). A generic label ("Submit", "OK") now defers to an ID that plainly names a reversible action, and the ID rule reads hyphenated IDs. On the 20 irreversible controls the code signals now catch 20 by element and 20 as a point (the Phase 6 classifier: 14 and 0), with 0 of 22 reversible controls flagged (was 1).
16. **YouTube never opened.** Its launcher activity is an inner class (`.app.honeycomb.Shell$HomeActivity`); `am start -n` went through the device's shell unquoted, so `$HomeActivity` became nothing and the launch failed silently. Launches now pass the component as an argument.
17. **The "Done" push waited for memory.** The finished event fired only after the task's memory was written, 10+ s after the phone work ended, so the Phase 5 check (and you) heard late. It now fires when the phone work ends.
18. **"Is Bluetooth on?" was answered with a row's words.** The agent read the answer from the Bluetooth switch, but switches were never outputs, so the routine reported the nearest text instead ("Bluetooth · Connected devices > Connection preferences", a search result). An on/off answer beside a switch now compiles to the switch's state. The same routine ran in the wrong app: Settings' search is a separate package, which Wonder named as the app, so the routine opens the app its first step was in.
19. **A fixed message that is the answer had nothing to find it by.** Calendar's "Nothing planned. Tap to create." has no ID and no label in front of it, so the output was dropped and the routine answered nothing. A message of 12+ characters with no data in it is now found by its own words; on a day with events it is missing and the ladder answers instead.
20. **The bot-check detector cried wolf.** A Maps page mentioning "verify" was marked a bot check. It now needs the challenge's activity, or a nearly empty screen with the challenge's words.
21. **A price read from the wrong menu item, graded a pass.** Chipotle's routine found the price by its ID, `tv_price`, which every item on the menu has, so it read the first one ($2.30 for Chips, asked about Chips & Guacamole at $5.25). The answer had a price's shape, so the suite counted it right. Two fixes: a value whose ID every row shares is now read in the row showing the requested item (`{{menu_item_name}}`, which also keeps that input from being dropped as unused); and answers graded only by their shape are now also read by a person, against the screen the routine read them from (routine runs now keep that screen's text tree). A pass a person reads as the wrong value doesn't count.
22. **A "Copied" preview hid a detour.** YouTube's agent opened the first video to read its title, then went back to the results and read it there. The compiler drops a stretch that returns to exactly the screen it left, but the results page didn't look the same twice: after typing, Android's "Copied" clipboard preview sat over it. System UI's clipboard and screenshot previews are now left out of screens, like the keyboard.
23. **One workflow's app leaked into the next.** Starbucks' agent pressed Back and landed on Target's bot check, still open from the workflow before; it spent its steps getting back and hit the step limit. The suite now closes each workflow's app when it ends.
24. **Closing the keyboard is never a required step.** On the small screen, flight_status's "Tap Done to dismiss the keyboard" could no longer find Gboard's Done key (keyboard keys aren't part of the screen any more, finding 13's follow-up). The repair pressed Back, but the keyboard had already gone, so Back left the app and the agent took over (13 calls). A routine already moves a target out from under the keyboard itself, so a step that only closes it now compiles as optional, skipped whenever the next step is ready.
25. **A price before its details was dropped.** Amazon's first result reads "$16.49 ( $0.82 /count)", after a brand carousel's bare "$6.53". The compiler could read a list value that is a whole label, or a name before its details, but not a number before its details, so the routine answered with the product's name only. A number-like value leading a list element now compiles to the first element of that whole shape.
26. **The sponsored result's rating.** Play's results for "Duolingo" start with a sponsored app; the routine read the first "Average rating" (Pimsleur's 4.1, graded a pass by its shape). A label every result repeats is now read after the element naming the requested input. The compiler also reads every output back from the screen the agent answered from, and warns when it gets something else: that check found this case on its own.
27. **A page title that only says the label.** Settings' "Android version" page has that title above the "Android version · 15" row; the routine found the title, read past it and came back empty. A value recorded as part N of a row now skips elements with fewer parts.
28. **"Address" didn't match "Address: 20 W 34th St.".** A row written as label and value with a colon scored 0.6 against its own label, so Maps' strict scroll went past it 8 times. The label before a colon now scores like a " · " part (0.95).
29. **A lower-case answer could never be verified.** The agent's answer must appear on screen before a run counts (and compiles). The check looked for numbers and capitalized words, so a video title such as "lofi hip hop radio 📚 beats to relax/study to" had "nothing specific to look for" and the run ended unverified. All of the answer's words of 4+ letters must now be on screen instead.
30. **"The first video" read the search term back.** YouTube's agent tapped its "lofi hip hop" suggestion instead of typing, so the compiler saw no search and anchored the title on the term; it also preferred a shorter "Mix - <title> - …" row over the video row that starts with the title. At run time a fallback then returned the search box's own text. A tapped suggestion that is the input now counts as entering it, so the top result is read by its place (up to the separator after the title); rows the value starts are preferred; and no fallback returns an element that only shows an input.
