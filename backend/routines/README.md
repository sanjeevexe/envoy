# routines

App routines (design doc, App routines): one successful agent run (or the person's demonstration in teach mode) compiled into a small program with inputs, code checks before and after its steps, element-based locators, and local self-repair saved as versioned patches. Reruns make no model calls while every check passes. A routine the person shares with agents is also an MCP tool of its own (`api/sharing.py`, `mcp_server/server.py`); nothing here changes for that.

| File | What |
| --- | --- |
| `model.py` | The format: `Routine`, `Step`, `Locator`, `Check`, `StepAction`, `Extract`, `InputSpec`; `{{slot}}` templating, `{{date:day}}` for one part of a date or time input (`dates.py`), and `{{_field}}` for what a field already holds; YAML in the design doc's shape (single-key checks and actions). |
| `locators.py` | Multi-attribute scoring (resource ID, label, description, field label, type, parent and sibling text, list membership, position). STRICT 0.80 / RELAXED 0.60 / MARGIN 0.08, tuned on SkyLark (`eval/tune_locators.py`). `text_has` is a hard filter for input-based choices; data in IDs becomes a glob (`trip_row_*`). `nth` picks one of a uniform list's look-alikes by its place among them (a gallery's newest clip); with `text_has`, rows that show the input but say much else besides (Uber's results for a destination) are taken at the relaxed bar, as the relaxed rung would take them. Role `check` needs text evidence and the same element type. |
| `checks.py` | Checks evaluated in code (app in front, element present or absent, text visible, field value, toggle state, screen changed, signature similarity) and written automatically by diffing a step's before and after trees. |
| `compiler.py` | Trace → routine: confirm success, refuse a run that had nothing to do (a delete with nothing to delete, a setting already as asked), clean up (pop-ups, dead taps, back-tracks; scrolls become `scroll_until`; a correction is kept, not taken for a back-track: a round trip whose screens came to show what the goal asks for, and typing done during a round trip is moved to where its screen comes back), generalize with Muse Wonder (inputs, fixed text, booking data, outputs), add checks, input witness checks, and `verify()` by replay. A locator that still fits several look-alikes on its recorded screen is made to fit the one the run acted on: the inputs it shows (`text_has: "{{song_title}} by {{song_artist}}"`), else its place in a list that starts with a fixed item (`nth`, with a before-check on that item, so a scrolled list matches nothing), else it is kept and listed in the compile report's `ambiguous`. A row chosen by an input typed earlier in the run, which several rows show (Uber's results for "Piedmont Park"), is the first of them (`nth: 0`). A run that opened its app itself (the agent started on the home screen) starts with that app: the launch becomes the routine's fresh start, not a step. An after-check that keeps a row's label ("Music" of "Music · golden hour") also names an input its value shows (`text_has: "{{sound_title}}"`). No check is compiled on something only passing through a screen: a scroll indicator (Instagram's fast-scroll "Today", shown while the gallery moves), or what the same screen no longer shows when the next step starts. An after-screen caught mid-change (YouTube Music's Songs filter, 45 ms after the tap: chips and results gone while the list reloads) left a step whose only checks were absences; when none of a step's checks that something is shown holds on the screen the run went on from, its after-checks come from that screen ("Clear filters" shown). Outputs are read by structure (an input the goal names, a value's shape, every row of a plural answer, yes/no by presence), never by the example's own words; one read in the list row that names an input keeps the row's ID and is read only in a list (never an overlay that shows the input too, such as a mini player); one that reads something else on the run's own final screen is dropped, and a question with no readable answer isn't compiled. An answer the run's own check couldn't find in the tree, and that isn't there (Uber's fares, drawn under a tip that is), is read from the run's screenshot instead, kept only if that read gives the agent's answer; when the run's screen took 1.5 s or more to settle after the last step, a wait of that long (at most 5 s) comes before the read. A taught trace (`api/teach.py`: your demonstration through the live view, in the agent's format, with no reasons) compiles the same way, confirmed by your word, and is marked `source: taught`. |
| `executor.py` | Runs a routine: wait for before-checks (5 s), locate, act through the policy gate, settle on the after-checks themselves. Fallback ladder: wait and retry → relaxed match → pop-up handler → local repair (≤2 model calls per step, ≤5 per run) → full agent → ask the user. Proposes patches (new locator, updated check, inserted, replaced or removed steps). A target chosen by its place in a list (`nth`) is looked for back at the list's start, never further down, so a repair after it sees the start too. An output read in a list row (`in_list`) is read in the first row, in reading order, that shows the input as a part of its own. |
| `store.py` | The library in `data/routines/<name>/`: versions, trial → active or rejected (rollback), run history, the recompile flag (more than half of the last 6 runs failed), patch evidence with before/after screenshots. |
| `lifecycle.py` | A routine's versions across its runs: a run that succeeded after a local repair leaves patches, which become a version on trial; the next run decides it (active if it finishes on its own, otherwise rolled back). |
| `dates.py` | Dates and times a request implies ("tomorrow", "this Thursday", "at 17h for 30 mins"), worked out in code from the phone's date, so the model never computes one. |
| `screen_read.py` | Outputs the tree doesn't have (a page Chrome draws without one, Uber's fares), read from a screenshot by Muse Spark, which must quote the line; kept only if the value has the recorded shape. |
| `visual.py` | Finding a routine's recorded picture of a target on the current screen (Phase 6), scaled between screen densities; a match must be clear and unique. |
| `screens.py` | Screen helpers shared by the compiler, locators, checks and executor (a stored tree back to a screen, offline). |
| `matcher.py` | Request → routine: app, intent patterns, description similarity, then one Muse Spark call that confirms and fills inputs from the request and notes (values must appear there, and are written like the input's example: `.txt`, not `txt`). |

## Run it

```bash
uv run --project backend python scripts/compile_routine.py <task_id>          # compile one trace and print the YAML
uv run --project backend python eval/run_routines.py record|compile|new-inputs|variants|baselines
uv run --project backend python eval/run_matching.py
uv run --project backend python eval/routines_report.py                      # eval/results/phase2/report.md
```
